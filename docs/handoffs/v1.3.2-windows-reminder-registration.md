## Behavior delivered

- Enabling reminders now registers the OS scheduler before persisting
  `enabled=true` or invoking the first worker check.
- A registration failure never invokes the worker, never sends an activation
  message, and leaves no new scheduler marker or enabled config.
- If the first check fails after registration, the previous disabled config
  and reminder ledger are restored and the new task/marker is removed. SMTP
  configuration and the DPAPI credential are not modified.
- Windows `PermissionDenied`, `Access is denied`, and `0x80070005` failures map
  to a short Chinese instruction to close the app, wait about 10 seconds, and
  run `start-local.cmd` once as administrator. Raw PowerShell stacks, mojibake,
  and personal paths are not returned to the browser.
- The UI treats reminders as active only when saved config and the scheduler
  marker both confirm installation. Step 3 must be green and show
  “后台提醒已开启”. A successful check with no new articles sends no mail.
- The Windows task remains current-user, interactive-logon, and `RunLevel
  Limited`; routine app startup does not require administrator rights.

## Deterministic regression evidence

The scheduler and worker are simulated; no real SMTP connection or email is
used. Tests prove:

1. permission failure occurs before the worker and preserves config, synthetic
   DPAPI ciphertext, and the reminder ledger;
2. no scheduler marker or enabled state remains after registration failure;
3. each known Windows permission signature returns the same safe Chinese hint;
4. unknown failures keep a short diagnostic without stack, mojibake, or personal
   absolute paths;
5. successful registration precedes persisted enablement and the first check;
6. first-check failure restores config and ledger and unregisters the new task;
7. the UI stays disabled and step 3 does not turn green after permission error.
