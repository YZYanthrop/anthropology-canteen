# v1.3.4 r1：缺失 LaunchAgent 的默认错误包装丢失诊断

2026-10-06；新确认产品缺陷，未修复，阻止重新发行。产品 S=`946cc16aae10e2ffda6fb8104d9576b21b317756`，版本 1.3.4、修订 r1。

## 触发、预期和实际

原生 macOS 15.7.9 两架构，普通用户 UID 501、有 gui launchd 会话；为唯一新测试身份注册后台提醒，先查询尚不存在的任务。
原生 `/bin/launchctl print gui/501/<unique-label>` 的完整 stderr 为：

```text
Bad request.
Could not find service "<unique-label>" in domain for user gui: 501
```

预期：识别任务不存在；只读状态显示 missing；注册可继续创建本次任务，且更新期间不执行 worker。
实际：原 ZIP 默认 `run` 调用 `schedulerCommandError` 后只保留首行，得到 `SCHEDULER_COMMAND_FAILED` / `计划任务操作失败：Bad request.`，注册在 bootstrap 前失败。
同 S 注入完整原生诊断另行证实只读状态变成 unknown；此状态结论是源码注入证据，不冒充额外原包页面测试。

## 根因和现有测试的盲点

`reminder-scheduler.mjs` 的 cleanSchedulerDiagnostic（约157行）只选首条可显示诊断；schedulerCommandError（约175–245行）将其变成新 Error，未保留“缺失任务”的机器可读分类。
默认 run（约247行）使用该包装器；macJobLoaded（约418行）只在 error.message 匹配 `Could not find service|service not found`，因此无法识别第二行。
现有 macOS basic scheduler harness 的 runCommand（packaging/macos/basic-acceptance/scheduler.mjs，约103行）保留完整 stderr。其源码+真实任务验收能通过，不证明产品默认命令包装器可用。
没有替换 ZIP 内实现。两份原包 native-smoke.log 都指向解压原包 reminder-scheduler.mjs:241/251；这个失败不能作为测试工具缺陷忽略。
