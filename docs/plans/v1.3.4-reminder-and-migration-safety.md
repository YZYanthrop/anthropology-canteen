## 问题与目标

只处理四个隐患：后台任务更新失败可能损失原任务；资料迁移恢复失败可能被隐瞒；后台状态
可能把停用或无法核对显示为正常；寻找旧版本失败可能影响本文件夹正常资料的读取。
用户应能知道提醒的真实状态和资料恢复的结果，并保留继续恢复的机会。

本轮只做静态核对，不把代码路径分析写成已经执行过故障测试：

| Slice | 已发布代码中的核对点 | 实施时先建立的回归证据 |
| --- | --- | --- |
| A | Windows 注册脚本只在部分分支恢复 XML；注册后检查抛异常不一定进入恢复。`installScheduler` 写本地任务记录，`enableReminderTransaction` 的 install 在 try 外，后续失败又会调用卸载 | 让每个失败边界在 v1.3.3 基线上重现，证明原任务、启用状态、设置和记录能够一并恢复 |
| B | `installMigrationFiles` 在写入、同步、关闭临时文件之后才加入 prepared；恢复与清理的异常被忽略，上层只记录 write-failed | 证明临时文件写入失败及恢复再次失败可观察，且恢复材料不会被清理或重启后覆盖 |
| C | `Test-ReminderTaskDefinition` 核对触发器数量和时间，未核对任务和触发器的启用状态；读取权限不足时 `getSchedulerStatus` 可凭旧记录返回 installed | 证明停用、缺失和无法读取均不能使页面显示后台提醒正常 |
| D | `findSiblingMigrationCandidates` 扫描失败返回 null，调用方读取 candidates.length；`readLocalDataFile` 先等待迁移检查 | 证明父目录拒绝访问不影响正常当前资料，且扫描错误不等同于没有旧资料 |

## Slice A：后台任务更新失败后，保住原任务

**用户结果：** 一次更新失败不会让原来可用的后台提醒消失；原来停用的任务也不会被悄悄开启。

范围与处理规则：

1. 任何修改前确认目标任务归属，保存原任务是否存在、完整定义、任务及触发器启用状态、
   原用户身份与运行权限、设置和本地任务记录；不存在的记录也要明确记录为不存在。
   无法可靠读取必要原状态时停止修改，不能把读取失败当作“原先没有任务”。
2. 将注册、注册后检查（含返回不合格及抛异常）、辅助结果返回、本地任务记录写入和设置
   写入纳入同一套失败处理；为每一步记录是否实际完成，避免两个层级重复卸载或误删原任务。
3. 原先有任务：恢复同一任务的原定义与启用状态，再核对恢复结果，并恢复设置和本地记录。
   原先没有任务：只清理本次确实创建的任务和记录，不按名称前缀或不明归属删除其他任务。
4. 恢复中的任一步失败时保留原状态快照和诊断依据，明确提示“更新失败，恢复未完成，需要处理”，
   不声称“没有更改”或“已恢复”；后续重复操作先核对未完成状态，不继续盲目覆盖。
5. 沿用 v1.3.3 的普通权限优先和受限任务小工具；提升和恢复都绑定原登录用户，保持
   `Interactive`、`RunLevel Limited`，不得提升整个应用或把任务转到提供管理员凭据的账户。
6. 取消权限确认只有在确认未发生修改时才显示“没有更改”；若之前已发生局部修改，按真实
   恢复结果提示。更新与恢复都不得调用 worker 或发送邮件。

验收：

- A1：原任务存在且开启、存在但停用、原任务不存在三种前态均覆盖；更新失败后逐项比较
  任务定义、任务/触发器启用状态、身份权限、设置和本地记录。
- A2：分别注入注册失败、注册后检查抛异常/结果不合格、辅助结果写入失败、本地任务记录
  写入失败、设置写入失败；新任务分支只清理本次新增，旧任务分支恢复原任务。
- A3：取消 UAC、恢复注册失败、恢复设置/记录失败、恢复后核对失败，均给出真实结果；
  未完成恢复不能继续显示提醒正常，也不能丢失恢复依据。
- A4：连续执行、失败后重试、成功后再更新及重启后再操作，当前提醒身份的任务不增加；
  无关任务不变，迁移路径的 worker 调用次数和发信次数均为 0。

预计位置：`reminder-scheduler.mjs`、`portable-server.mjs`、`tools/register-windows-reminder.ps1`、
`tools/elevate-windows-reminder.ps1`、`tools/windows-reminder-task-common.ps1`；
`tests/reminder-activation.test.mjs` 和必要的 UI/Windows 临时任务验证。

## Slice B：资料迁移失败后，不留下不明状态

**用户结果：** 区分迁移写入失败、原资料完整恢复、恢复未完成和清理失败；保留人工恢复机会。
不承诺任何磁盘故障都能自动恢复，底线是不隐瞒失败、不破坏恢复机会。

范围与处理规则：

1. 临时文件一旦创建，立即纳入可追踪的清理/恢复集合，覆盖写入、同步和关闭句柄失败；
   保留主错误与后续恢复/清理错误，不能用一个笼统 write-failed 吞掉恢复结果。
2. 为每个目标记录原有内容是否存在、备份、替换进度和恢复结果。只有确认所有应恢复资料
   都恢复到原状态，才允许显示“当前资料已恢复”；备份存在本身不等于恢复成功。
3. 恢复未完成时保留备份、必要临时文件及可识别的恢复信息；停止该迁移的自动重试与覆盖。
   重启后仍须识别未完成恢复，不得重新初始化空白资料，也不得仅靠进程内变量防护。
4. 清理只处理已证明不再需要的本次临时文件。清理失败单独报告，不把成功恢复误报为完全成功，
   也不因清理失败再次替换资料；恢复材料不得被盲目批量删除。
5. 旧版来源只读。保留当前非空设置、授权码和发送记录，沿用同源迁移与唯一身份匹配规则；
   在现有锁和替换前核验下，防止扫描/恢复期间新写入的资料被旧副本覆盖。
6. 未完成恢复时，只允许确认安全的资料读取；任何会覆盖待恢复目标的自动写入都必须停止，
   向用户说明需要处理的步骤，日志/接口不暴露授权码或个人路径。

验收：

- B1：临时文件创建后在写入、同步、关闭阶段分别中断；确认残留可追踪，原目标未被错误替换。
- B2：分别使备份、第一/后续文件替换失败，模拟文件占用、权限拒绝及恢复再次失败；记录
  每个目标的真实结果，不能在任一未恢复时给出成功恢复提示。
- B3：单独注入清理失败；必要备份和恢复材料仍在，可重试清理的无用残留与需人工处理的
  恢复材料可区分。
- B4：替换中断/恢复未完成后重启，仍阻止自动覆盖并提示；恢复完成后重启可正常读取。
- B5：已有新资料、非空设置、凭据和发送记录时不覆盖；对比旧版来源前后字节及目标关键
  状态。迁移/恢复不触发发信、立即检查或发送账本重置。

预计位置：`portable-server.mjs` 的 `installMigrationFiles`、迁移结果及启动读取路径，
`tests/reminder-migration.test.mjs`、`tests/portable-data.test.mjs` 和对应提示测试。
`packaging/shared/import-data.mjs` 只核对相关恢复合同；若相同故障也存在于其恢复流程，
先补复现再在本 Slice 内修复，不重做导入格式或导入功能，不修改平台导入启动器。

## Slice C：如实显示后台提醒状态

**用户结果：** 状态来自本次系统核对；任务或触发条件停用不会显示为正常开启。

- 检查 Windows 任务本身、每日触发器、登录触发器是否启用，同时保留路径、时间、身份和
  受限权限核对。缺失与错误定义、明确停用、读取失败分别处理。
- 不能读系统状态时，不以旧记录、配置 enabled 或上次成功时间宣称当前正常。
  旧记录可作为历史信息，不能点亮“已开启”；共享接口仍须兼容。
- 发现停用只提示；只有用户明确选择重新开启后才修改系统任务。只读状态查询、页面刷新、
  启动和数据迁移不会自动重新启用任务或触发器。

| 显示状态 | 必要证据 | 主要操作与约束 |
| --- | --- | --- |
| 已开启 | 已保存配置开启，系统任务定义正确，任务及每日/登录触发器均启用 | 显示停用操作；无已知缺陷或未知状态时才能显示正常 |
| 已停用 | 确认任务或所需触发器停用，或用户已明确保存停用设置 | 说明停用原因，提供明确的重新开启选择，不自动修改 |
| 需要更新 | 任务存在且可核对，但路径、时间、所需触发条件或定义不符合当前要求 | 允许安全归属下由用户更新；涉及身份不明时先停止修改 |
| 任务不存在 | 系统查询成功且确认目标不存在 | 明确说明需重新创建，由用户操作；不根据缺少本地记录猜测 |
| 无法核对 | 权限不足、检查失败、结果不完整或归属不明确 | 提供重新核对/处理说明，不显示绿色正常，不自动修复或提升权限 |

多项问题并存时，不丢失原因；无法核对时保守显示，明确停用不能被“路径正确”掩盖。
macOS 不新增调度功能；共享状态显示变化须保留其接口兼容性，不能因 Windows 修复改变
LaunchAgent 的已有启停语义或把无法核对写成已确认正常。

验收：任务停用、仅每日触发器停用、仅登录触发器停用、缺失触发器、旧路径、任务缺失、
权限不足及其他检查异常分别覆盖；旧本地记录仍匹配时也不能掩盖问题。测试状态文案、
按钮可用性及点击语义；刷新状态无系统写入，重新开启只在明确用户操作后发生。
