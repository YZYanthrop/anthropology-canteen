# 版本与发布流程

## 两种编号各司其职

- “第 12 版”是内部迭代编号，用来记录做过多少轮设计和试验。
- `v1.0.0` 是对外发布编号，用来表达兼容性和改动程度。

内部迭代无需与公开版本一一对应。第 12 次迭代成为首个稳定公开版本，因此命名为
`v1.0.0` 是合理的。

## 语义化版本

公开版本使用 `主版本.次版本.修订版本`：

- `1.0.1`：修复缺陷，不改变已有使用方式。
- `1.1.0`：增加向后兼容的新功能。
- `2.0.0`：有不兼容变化，例如数据格式或操作流程发生重大调整。

尚未稳定、需要试用的版本可使用：

- `1.1.0-beta.1`
- `1.1.0-beta.2`
- `1.1.0-rc.1`

## 日常开发

1. 为一个明确目标建立分支，例如 `feature/better-journal-search` 或
   `fix/data-migration`.
2. 小步提交，每次提交只表达一个完整意图。
3. 推送分支并建立 Pull Request，检查差异和测试结果。
4. 通过检查后合并到 `main`；`main` 应始终保持可发布。
5. 把用户可感知的变化写入 `CHANGELOG.md` 的“未发布”部分。

推荐提交信息：

- `feat: add journal search`
- `fix: preserve migrated subscriptions`
- `docs: clarify Windows startup`
- `chore: prepare v1.1.0`

## 正式发布

1. 确认工作区没有个人数据、密钥、缓存或旧构建产物。
2. 运行 `pnpm lint` 和 `pnpm build`。
3. 更新 `package.json` 和 `CHANGELOG.md` 中的版本与日期。
4. 提交：`chore: release v1.1.0`。
5. 在该提交上创建带说明的 Git 标签：`v1.1.0`。
6. 推送提交和标签，在 GitHub 创建同名 Release，并上传 Windows ZIP。
7. 下载一次发布附件并核对 SHA-256，确保用户拿到的文件与本地一致。

## 简单决策法

先问：“用户升级后，原来的数据和用法还兼容吗？”

- 兼容，只修问题：加最后一位。
- 兼容，增加能力：加中间一位，最后一位归零。
- 不兼容：加第一位，其余归零。
