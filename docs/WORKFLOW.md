# 对话与项目工作流

## 核心做法

不再维护一个永久增长的“主对话”。每个对话只处理一个明确阶段，长期状态保存在 Git
和项目文档中：

1. `docs/CURRENT.md`：任何新对话都能快速掌握的稳定事实。
2. `docs/work/ACTIVE.md`：当前正在规划或执行哪一个工作包。
3. `docs/plans/`：经过讨论的版本或功能方案。
4. `docs/handoffs/`：一次实现完成后的可验证交接记录。
5. Git 分支、提交和测试结果：代码是否真正完成的最终证据。

因此，一个旧对话即使被归档或删除，也不会影响继续开发。

## 三类短对话

### 1. 方案对话

用途：澄清问题、比较方案、划定范围和验收标准。原则上不修改产品源码。

产物：

- 新建或更新一份 `docs/plans/<版本>-<主题>.md`；
- 把 `docs/work/ACTIVE.md` 指向该计划；
- 状态从 `Proposed` 变成 `Approved` 前，不进入实现。

一个版本如果包含互不依赖的多个大问题，应在计划中拆成多个可独立验收的 slice，随后
分别交给短实现对话，而不是让一个对话包办整个版本。

### 2. 实现对话

用途：只执行一份已批准计划，或其中一个明确 slice。

开始时：

- 读取 `AGENTS.md`、`docs/CURRENT.md`、`docs/work/ACTIVE.md` 和指定计划；
- 按 `docs/CURRENT.md` 的路由，只读取与改动相关的架构或平台文档；
- 从最新可发布基线建立短期 `codex/` 分支或隔离 worktree；
- 检查并保留其他工作区中的未提交修改。

结束时：

- 完成测试和适用的原生 smoke；
- 更新计划状态、`docs/CURRENT.md` 及必要的项目文档；
- 写入 `docs/handoffs/<版本>-<主题>.md`；
- 提交改动，记录分支、提交、测试和剩余限制；
- 不在未明确授权时推送、打标签或发布。

### 3. 发布对话

用途：仅在所有实现 slice 已合并并形成确定提交后进行版本冻结、三平台候选构建、标签
和 Release 工作。

发布对话不继续开发功能。若发现产品缺陷，应退回新的实现对话；不能在打包过程中临时
修改源码后继续发布。标签、推送和 GitHub Release 仍需使用者明确授权。

## v1.3.4 r1 的一次性发行边界

当前[重新发行目标](plans/v1.3.4-three-platform-reissue.md)明确允许从独立修订分支冻结 S 并直接发行，
不要求先合并 main；没有 main 推送授权。先在 S 完成新三包构建/验收，再发布同一组字节，标签不触发重建。
用户已批准门槛满足后的精确公开操作；执行前仍保存实际对象清单和回退范围，不重复请求相同许可。
任何产品缺陷、必需项缺失或清理失败均不能自动豁免；产品修复转新的明确任务，测试工具修正可在原包上重验。
此例外不改变其他版本的正常边界，不把有限范围验收写成整个版本 Verified。

## 状态机

每份计划只使用以下状态：

`Proposed → Approved → In progress → Verified → Merged → Released`

也可以从任意未发布状态变为 `Cancelled`。同一时间只能有一个 `In progress` 的主工作
包；多个 slice 并行时，`ACTIVE.md` 必须列出各自分支，避免修改重叠文件。

## 对话命名

- `方案 v1.3.2：可用性与恢复能力`
- `执行 v1.3.2-A：文章状态与日期`
- `执行 v1.3.2-B：导航与更新状态`
- `发布 v1.3.2：Windows + macOS`

不要继续使用 `first version`、`first version (2)` 或永久的“Mac 适配”对话。名称应让
人一眼看出版本、阶段和范围。

## 可直接复制的新对话开场语

### 方案对话

> 请读取 `AGENTS.md`、`docs/CURRENT.md` 和 `docs/work/ACTIVE.md`。本对话只负责制定或审阅
> `<版本/主题>` 方案，不修改产品源码。把最终方案写入 `docs/plans/`，列明范围、非目标、
> 兼容性、验收标准、测试和 slice；不要依赖任何旧对话内容。

### 实现对话

> 请读取 `AGENTS.md`、`docs/CURRENT.md`、`docs/work/ACTIVE.md` 和其中指定的已批准计划。
> 只执行 `<slice>`，从最新可发布基线建立短期分支，保留其他未提交改动；完成源码、回归
> 测试、适用文档和 `docs/handoffs/` 交接。不要读取旧对话，也不要推送、打标签或发布。

### 发布对话

> 请读取 `AGENTS.md`、`docs/CURRENT.md`、`docs/work/ACTIVE.md`、相关计划与 handoff，以及
> `docs/RELEASING.md`。先只读核验所有 slice 已合并且提交唯一，再按照三平台发布流程准备
> 候选；任何推送、标签或 Release 动作都先取得我的明确授权。

## 何时可以归档旧对话

以下条件全部满足后即可归档，不需要保留它作为项目记忆：

- 改动已提交，或明确记录为取消；
- 分支已合并，或在 `ACTIVE.md` 中记录了保留原因；
- 计划与 handoff 反映真实状态；
- 必要的 `CURRENT`、架构、平台、发布和版本记录已更新；
- 下一对话可以只靠仓库文件继续。

## 每周维护上限

`CURRENT.md` 应保持简短，只记录当前事实；`ACTIVE.md` 只保留当前工作包。完成版本的详细
过程进入 `CHANGELOG.md` 或历史文档，不复制回入口文件。若入口文件超过约 100 行，应
删去历史叙述并改成链接。
